# Webアプリの変更前後を試す

## 対象と役割

既存の適用対象はOpenEMR・OHIF Viewer・MONAIの3件で、今回選び直していない。Webアプリの試用は、保存と再表示の自動試験があるOpenEMRから接続する。OHIFとMONAIへの適用目標も維持する。

技術者は構成図と質問を使って調査し、正常時と失敗時の動作を検証する。利用者は `/user-trial` から変更前後のアプリを操作し、感想を残す。構成図を見ることやコードを読むことを、試用開始の条件にしない。

最初の相談例は「問診を保存しても画面が変わらず、保存できたのか分からない」という仮想事例。OpenEMRでこの問題が起きると確認した意味ではなく、都合のよい不具合や改善効果を作って実績に数えない。実際の変更内容は、対象コードと動作を調査して決める。

## 技術者が準備する

1. OSSの変更前後を、異なる40桁のコミットIDで固定する。上流と研究用のforkを比較する場合も、各版の実際のリポジトリとコミットを指定する。
2. 本番のデータ・認証・接続先を使わず、試用環境を別々に起動する。OpenEMR用の補助コマンドは [OSS試用環境の手順](web-oss-trial.md)を参照する。
3. `/` の構成図と質問、`/workbench` の技術検証を使って調査する。保存結果、重複、失敗時の表示、所要時間など、実際に確認した範囲を記録する。
4. `/user-trial` の「技術者が試用を準備する」を開く。改善したいこと、利用者の操作、試験用データ・初期状態・環境・起動と終了の手順を入力する。
5. AとBのリポジトリ・コミット・コード参照・URLを登録する。対応する技術検証の根拠IDがあれば指定する。別のコミットの根拠は登録できない。根拠がない場合も計画は作れるが、検証済みとは表示しない。
6. 利用者と同じ試用端末のブラウザで `/user-trial` を開く。当初は開発者が同席する想定。外部公開や遠隔共有の仕組みは追加していない。

試用先はlocalhostまたはループバックIPのHTTP(S) URLに限る。URLに認証情報・クエリー・フラグメントは入れない。アプリにログインが必要なら試用専用のアカウントで操作する。麦漆のトークンをURLへ付けない。

登録したコミットとURLの対応は技術者の申告であり、基盤による配備コードの同一性の証明ではない。ポートが違うだけではCookieが分離されないため、異なるホスト名か別のブラウザプロファイルを使い、ログイン状態の混在を確認する。

## 利用者が試す

1. 試す内容を選び、参加者番号などの識別名を入力する。氏名・職種・本人確認を自動で確定する機能ではない。
2. A→BまたはB→Aを選び、試用記録を開始する。順序は計画と一緒に保存する。
3. 案内されたアプリを別タブで開き、決めた操作を試す。リンクを開いただけで試用済みにはしない。
4. 麦漆へ戻り、実際の操作、操作を終えたか・途中で進めなかったか・試せなかったかと、感想・理由を記入する。
5. もう一方でも同じ操作を試して記録する。保存済みの感想は上書きしない。途中から再開する場合は「続きを記録する」を使う。

本番の患者情報や認証情報は記入しない。途中で試せなかった場合も、その理由を残せる。

## 記録と再試用

計画は登録時の条件版・実行条件・固定コミット・根拠IDと一緒に保存する。計画を編集するAPIは設けず、条件が変わったら新しい計画を作る。計画作成後に事例の条件や実行条件が変わった場合、新しい試用の開始を拒否する。開始済みの試用の感想は、元の計画へ追加できる。画面と確認資料には、古い条件に対応する記録であることを表示する。技術検証の根拠IDからは、該当する版の過去の試行を開ける。

同時更新は事例の版で検出し、古い画面からの書き込みを拒否する。試用記録は既存の事例の版として、一時ファイルへの書き込みと同期後、完成した版だけを公開する方法で保存する。APIの応答が失われた場合は記録を読み直し、二重に感想を追加しない。

利用者の操作と感想は本人または記入者の申告。自動で操作を観測した証拠、本人確認、品質検証の通過、採用の合意とは区別する。自動試験の判定と「採用する」の制限は変更しない。一件の比較から統計的な改善効果を主張しない。

試用記録を持つ事例は形式3になる。旧形式1・2を引き続き読めるが、形式3を旧バイナリで更新することはできない。全版バックアップは試用の計画・感想も保持する。確認資料には版と根拠参照と申告内容を含め、試用URLや実行条件の生のスナップショットを出力しない。自由記述に含まれる情報は共有前に確認する。

## 未確認の範囲

大学病院関係者の知り合いに操作協力をお願いする想定だが、参加者の確保と実際の評価は未実施。環境の起動手順、画面の操作試験、実利用者による改善の確認を別々に記録する。医療業務上の有用性や、任意のOSSの自動準備を今回の機能だけで確認済みにしない。
