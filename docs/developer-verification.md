# 医療システム開発者の技術的な検証

## 現在の対象と目的

主な対象は医療システムを提供する開発者。構成とコードを調べ、対象の版・検証条件・実行時の観測・結果・未確認事項を対応づける。要件の把握と検証に必要な知識や作業が、新規参入の負担になるという課題意識を持つ。

方針の出所は2026年10月25日の本人の発言と[#184](https://github.com/Suisan-neki/mugiurushi/issues/184)。

> 自分は技術的な検証をしたいのに多分ユーザーまでステークホルダーにすることでズレたと思う

> 医療情報における参入障壁の高さみたいなのも書きたいよね、満たすべきものも多いし

> この認識でちゃんと作り直そう、非技術者に主体を置きすぎてズレてた

以前の非技術者との共同理解や利用者による改善確認を中心にした計画より、今回の指示を優先する。利用者の試用・感想や開発者との合意を中核機能の完了条件にしない。対象システムの業務条件を把握する必要性は残るが、麦漆そのものを利用者の要望受付・使いやすさ評価を主目的とする製品にはしない。

## 開発者の操作

| 段階 | 開発者が確認・設定する内容 | 残す記録 |
| --- | --- | --- |
| 対象を固定する | リポジトリ・コミットと調査対象の処理 | 固定したコードへの参照 |
| 構成を調べる | 処理・外部依存・通信・保存先と障害が影響する範囲 | 図・コードの根拠・未読の範囲 |
| 検証条件を決める | 正常時と障害時の条件・期待する結果・観測方法 | 条件の版・観測規則・未確定の条件 |
| 実行する | 対象の版・イメージ・起動方法・障害条件・資源の扱い | 実行レシピ・観測・中断や失敗の記録 |
| 結果を読む | 応答・表示・ログ・保存状態と不足や食い違い | 判定の根拠・未確認事項 |
| 再検証する | 修正後の版・条件差分と以前の結果の適用範囲 | 再試験と比較・再確認が必要な根拠 |

構成図と対話は調査の手段として使う。既に検証内容が決まっていれば`/workbench`から直接進める。入口の記録済み項目から設定や結果へ戻れる。

## 今回の設計変更

- 最初の技術者／非技術者の選択を廃止する。技術情報を含む表示を既定にする。
- 概要表示は説明の詳しさだけを変える。記録者・条件・根拠・判定を変更しない。
- 新規の記録者は開発者を既定にする。既存の名前や役割を説明の切り替えで上書きしない。
- AIへ技術的な検証の目的を渡し、処理・障害条件・期待する結果・観測方法を整理させる。エンドユーザーの困りごとや試用・合意を前提にしない。
- NativeとDifyの双方に同じ検証目的を渡す。Difyの公開済みChatflowそのものの編集は今回の対象にしない。実Difyでの回答品質は別途確認する。
- 対象の構成モデルや試験設定を引き継ぎ、実行の成功と観測条件を満たすことを区別する。

## 互換性

保存済みの事例・試行・図・対話・試用計画・感想は変更しない。`/user-trial`と既存の試用用APIは引き続き扱うが、通常の検証導線からは外す。

`audience`の`developer`と`operator`は既存の入力形式を保つ。現在の画面ではそれぞれ技術情報と概要の表示に使い、記録者の役割には転用しない。旧画面の`eel-audience`による立場選択は初期表示に使わない。`eel-person`に明示して保存した名前と役割は維持する。旧画面が立場選択から自動作成した匿名の記録者だけを新しい既定へ移し、保存済みの発言は書き換えない。

過去の人による確認の状態は既存の形式を保つ。一人の開発者が確認した場合にもう一方の担当を必須と誤読させる文言を除く。人による確認の数を技術的な検証結果に読み替えない。未達や判定不能の条件がある場合に採用判断を拒否する現在の規則は維持する。

構成図の生成指示には新しい版を付ける。古い図はそのまま読めるようにし、新しい指示を適用する場合は利用者が同じコミットで作り直す。保存済みの根拠を無断で生成し直さない。

## 現在の実装と継続する課題

現在の実行方式と制約は[固定版実行](pinned-execution.md)・[固定環境](pinned-environments.md)・[ブラウザ試験](browser-trials.md)を参照する。OpenEMR・OHIF Viewer・MONAIを使った既存の試験例は引き継ぐ。例示だけで対象を固定した必須要件を追加しない。

`local`で起動する処理とブラウザ操作器はホスト上で動く。コンテナの対象をDocker内で動かすことと操作器まで隔離することは異なる。試験用資源の削除、新しい環境での再実行、対象システムの障害からの復旧、VMスナップショットからの状態復元を同じ機能として説明しない。コンテナ対象のDB故障（停止・切断・読み取り専用）は、試験案の`recovery`で解除し、復旧後の読み出しを故障中と比べられる。これは同じ試験環境内での解除であり、VMスナップショットからの復元や実運用の復旧手順の確認ではない。事例のバックアップ復元も対象環境の復元ではない。

次の技術課題として、本番への影響を防ぐ実行条件、状態の初期化、観測不足や矛盾の扱い、障害注入の時点と観測の対応を検証する。任意アプリの自動準備・自動計測やVMのスナップショット復元を実装済みとはしない。基盤だけで法令・ガイドラインへの適合全体や医療安全性を保証しない。

結果画面では、各試行の「コンテナの通信と隔離」「DB故障の解除と復旧後の比較」を開ける。記録した外部通信の方針と設定確認、接続元・接続先・件数・バイト数、故障解除後の準備確認と読み出しの比較を表示する。記録がない旧形式を通信0件や復旧済みと扱わず、故障中に読めなかった行数と、正常に読み出した0行を区別する。復旧できても元の判定を変更しない。中継状態が200以外の件数はアプリの失敗件数ではなく、未完了の接続の成否とバイト数は不明である。表示の追加で観測範囲は広がらない。

表示の確認は`npm run test:result-observations`で行う。実Rust APIで確認項目を作り、ブラウザが受け取る応答だけに合成の通信・復旧記録を差し込む。表示と互換性の確認であり、対象のコンテナやDBを実行した結果ではない。

## 比較評価の候補

次は実装側の評価案。人数・閾値・比較対象を本人の確定要件として追加しない。

- 対象と条件を固定して試験を始めるまでの時間と操作数。
- 同じ条件で再実行できるか。再現できない場合の差分と理由が記録されるか。
- 注入した障害と応答・保存状態・ログなどの観測を対応づけられるか。
- 観測の欠落や矛盾を成功にせず、判定不能とその理由を示せるか。
- 改修後に古い根拠をそのまま適用せず、条件差分と再検証を追えるか。
- 実行中断や失敗後の試験用プロセス・コンテナ・保存先を確認できるか。

既存の試験・観測ツールを組み合わせた方法と同じ対象・条件で比較する。参入障壁を実際に低減できたかは未計測。画面操作の合格を検証負担の軽減や医療機関での有効性の実証にしない。

今回の操作と互換性の確認は[検証記録](validation-developer-verification-2026-10-25.md)を参照する。
