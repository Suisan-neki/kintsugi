# 目的、試作の仕様、未決定事項

## 2026年10月25日 品質検証と利用者による改善確認

技術者向けの構成図・質問によるシステム理解と、実行・観測による品質検証を維持する。利用者は困っている操作を伝え、変更前後のWebアプリを試して感想を返す。利用者の構成図読解を必須にしない。

最初の適用対象は既存OSSとする。小さな自作アプリに都合のよい条件を作るだけで適用を確認したと扱わない。大学病院関係者の知り合いに操作協力をお願いする想定で、参加者の確保や評価の実施を実装開始の条件にしない。

対象の版・実行条件・検証結果を扱う部分を中心に開発し、担当範囲を徐々に広げる。相談・実装には既存の会話やGitHubを利用し、試用環境の起動は当初は手動でもよい。検証・試用の操作を本番へ影響させない要件を維持する。実行制限の保留PR #174は今回採用しない。

#84の仮想事例は「問診を保存しても画面が変わらず、保存できたのか分からない」。対象OSSで同じ問題が起きると確認した意味ではない。技術的な保存の検証と、利用者が完了を判断して次の操作へ進めるかを別々に確認する。合成データの操作試験と実利用者の評価も区別する。

今回の実装は[Web試用の記録と操作](web-user-trial.md)を参照する。以下は過去の方針・実装の経緯を含む。現在の対話で合意した範囲とREADMEを優先する。

## 2026年10月21日に本人が指定したAPIキーの担当

APIキーは開発者・運営者がサーバーへ設定する。利用者にキー、モデル名、接続先の入力を求めない。運営者の設定手順と、利用者が構成を理解して疑問・検証へ進む操作を混ぜない。

## 2026年10月21日に本人が指定した画面の順序

技術者／非技術者を選ぶ→GitHubリポジトリを読む→そのシステムのアーキテクチャ図を見る→不安や疑問を整理する→検証を開始して改善する。この順序を利用者向け画面の中心にする。

番号表示は問題意識を示す一例で、製品の必須題材ではない。デモとリポジトリの読取を並列の入口にしない。「モード設定の記入者」「モード設定の理由」は利用者へ入力を求めない。見本の対象・構成の版・試行・要素・接続を大量に選ばせる画面を、理解の入口にしない。

AIによる対話を後から接続できる位置に、構成図と疑問の記録を置く。AIの未接続を、固定した見本や自動回答で補わない。画面操作の試験と利用者の理解評価を区別する。

## 2026年10月21日に本人が明確にした構成図の意味

本人が求めるのは、システム全体を表す1枚の図を基に、誰でも分かる粒度に落とし込んだり、技術者向けに詳しく説明したりする機能。構成要素の役割・つながり・情報の流れを共有し、不安や疑問から検証と改善へ進むために使う。

共通の構成モデル、要素と接続の根拠、立場に応じた集約と詳細化は実装側の設計案。[構成図の設計修正](system-architecture-design.md)に例と完了条件を記載した。PR #168でサービスと役割・接続の抽出、同じ配置での立場別の説明、接続への疑問、元の部分への復帰を実装した。対応する静的な構文に限る試作であり、一般的な構成抽出と実参加者による理解の確認は #167で継続する。[実装と限界](repository-architecture.md)を参照する。

## 理解とテストの二つの機能

2026-10-07に本人が指定した製品の中心は理解とテスト。理解では公開GitHubから構成・入口・処理と根拠コードをたどる。テストでは対象の処理を実行して期待する動作・失敗・未確認事項を確かめる。両機能は別々に使えて同じコードと結果へ対応づけられるようにする。

公開リポジトリから始めることは本人が選択済み。理解の最初の試作は宣言・参照先の簡易解析と作者の説明の表示。任意設定のAI説明と確認候補を既存の期待・試験へつなぐ経路を試作している。実モデルによる意味の説明の品質・効用と、完全な処理解析は未検証・未実装として区別する。現在のテスト基盤の完成を製品全体の完成としない。詳細は[理解とテストの入口](repository-understanding.md)。

## 既存のテスト基盤で選んだ試作の仕様

| 項目 | 試作の扱い |
| --- | --- |
| データ | 架空の名前・年齢1件。空の名前と年齢151以上を拒否する既存判定を維持 |
| 操作 | CLIで条件を指定し、1回の送信を行う |
| 通信 | localhostのTCP、長さ付きJSON、最大64KiB |
| 保存 | 試行ごとの新規JSONファイル。書き込み・sync_all成功後に応答 |
| 表示 | 保存処理成功の応答を受信した場合だけDisplaySavedを記録 |
| 根拠 | 同じ試行・データ・送信試行に属するサーバーの保存記録を使う |
| 欠落・食い違い | 不足・矛盾をUnknownとし、独立した読み出しで埋めない |
| 再試行 | 新規ディレクトリを作り、previous_runで前の試行にリンク |
| 更新 | 条件・入力・コード・故障・実行環境の差を示す。変更された条件には旧規則を適用しない |
| 外部アプリ | プロセス記録を保存する。終了だけでは業務条件を判定しない |

| 共同レビュー | 同じ端末の画面で認識・出所・未回答と人の判断を保存。立場は自己申告 |
| 根拠の更新 | 条件版と宣言した依存先を照合し、古い根拠をUnknownにする。最新の不足を古い成功で埋めない |
| 比較資料 | 元の情報をそろえた4種類の資料と未記入の回答欄。通常のチェックリストの限定した参照実装も追加。利用者評価は未実施 |

## 理解と試験の画面で追加した試作（10月14日）

本人の依頼で確認済みの目的：公開GitHubのURLから始め、理解・期待の確認・実際の故障を含む試行・結果の確認・修正後の再試験を一つの流れで行う。技術者と非技術者が、期待、実際の結果、まだ分からないことを同じ記録で確認する。終了コード0だけを成功にせず、人が確認していない内容を「合意済み」にしない。

Codexが選んだ試作の仕様（本人の採用前）：

- 実行できる対象はNode.jsとPython。依存関係のインストールは行わない。
- 判定の範囲は「受付」「書き込み」「後から読み出せた」。同じ範囲の観測が食い違うと判定できないにする。
- 確認は名前と役割の自己申告で、運用担当と開発者の両方が現在の条件の版で確認したときだけ「両者が確認済み」と表示する。
- 故障は、保存先の書き込み不可、保存先と同名のディレクトリ、基盤による読み出しの停止、ネットワークの遮断（bubblewrapの場合だけ）。

未決定の業務条件：誰が確認する必要があるか、確認者の本人確認の方法、許容する待ち時間、医療機関の稼働環境で使える実行方式、外部公開時の認証。詳細は[理解と試験の画面](understand-and-test.md)と[判断理由](implementation-decisions.md)。
